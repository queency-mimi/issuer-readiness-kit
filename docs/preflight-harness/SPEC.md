# SPEC: preflight-harness (normative)

Status: scaffold, 2026-10-31. Package `@sik/preflight-harness`, ticket prefix `PFH`.
Trust tags: [P] primary source read (URL/path and date), [S] secondary (discovery notes, other agents' runs), [V] vendor, [I] inference, [E] estimate, [U] unverified (spike exists). RFC 2119 key words apply.

## 0. Scope

A **differential test harness** for libraries that answer "can this destination receive this asset?". It runs the same fixture set through several libraries, normalises each answer to one verdict type with typed reason codes, and reports where they disagree, where they miss something, and where they contradict ledger or simulation evidence. It also exports a **DTC registered-wallet readiness scenario pack** for dtc-kit's runner.

It is read-only. It never signs, never submits a payment, never calls a SEP-8 approval server, never holds keys. The single exception is the **testnet seeding** step of fixture capture (SPEC 2.3.3), which uses throwaway keys generated at runtime on testnet only.

Not a sixth receive-check library (the discovery note's explicit advice: "Do not ship a sixth library"). Not a batch/payout tool. Not a replacement for SDF's `preflightPayment` (js-stellar-sdk issue #1601, open as of the note [S]). Nothing here may be described as DTC-compatible (G-DTCC).

## 1. Data flow

```
 fixtures/cases/<id>/{case.json, state.json, truth.json + *.provenance.json}     <- captured by script (section 2)
        |
        v   StateSnapshot (library-neutral)                        ground truth (Horizon result / simulation)
 adapter.replay(case, snapshot)  --- feeds each library's injection point --->  library output (raw)
        |  map codes through library-maps -> ReasonCode; derive verdict (section 4)
        v
 ReceiveVerdict[]  --->  buildDiffReport(cases, truth, verdicts)  --->  out/report.json + out/report.md
                                                              (matrix, agreements, findings)
 DtcScenarioDef[] + cases ---> evaluateDtcReadiness ---> buildScenarioPack ---> out/dtc-wallet-readiness.pack.json
```

## 2. Fixtures

### 2.1 Layout

```
fixtures/cases/<caseId>/case.json              CaseFile (schemas/case.schema.json)
fixtures/cases/<caseId>/state.json             StateSnapshot (schemas/state-snapshot.schema.json)
fixtures/cases/<caseId>/state.provenance.json  (schemas/provenance.schema.json)
fixtures/cases/<caseId>/truth.json             GroundTruth (schemas/ground-truth.schema.json), when obtainable
fixtures/cases/<caseId>/truth.provenance.json
fixtures/synthetic/<caseId>/...                hand-specified states for unit tests only (provenance kind "synthetic")
```
`caseId` matches `^[a-z0-9]+(\.[a-z0-9-]+)+$`. A case is **catalogued** (an entry in `src/fixtures/catalogue.ts`) before it is **captured** (`captured: true` and files present). At scaffold time 0 of 32 cases are captured; 2 synthetic fixtures exist (generated by `scripts/make-synthetic-fixtures.ts`).

### 2.2 StateSnapshot

Library-neutral facts: accounts (or `null` for non-existent) with flags, data entries (base64), trustlines (balance, limit, buying/selling liabilities, `authorized`, `authorizedToMaintainLiabilities`, `clawbackEnabled`); contracts (`exists`, `kind` sac/wasm, `wraps`, recorded read results); SAC balances keyed `sacId:holder`; **recorded simulations** (`call` string, `source`, result ok or `{error, contractErrorCode}`); optional directory and federation answers; `networkParams` (base reserve and fee); `ledger` and `capturedAt`. Amounts are stroops as decimal strings. Horizon and RPC reads are **not atomic with each other**; `provenance.readsAreAtomic` is always `false` (stellar-check's report carries `atomic: false` for the same reason [P: `src/types.ts`]). The snapshot `ledger` is the RPC `getLatestLedger` at capture.

### 2.3 Capture (PFH-020..023)

1. **Read-only capture** (mainnet or testnet): Horizon `GET /accounts/{id}` (balances incl. `is_authorized`, `is_authorized_to_maintain_liabilities`, `is_clawback_enabled`, `limit`, `buying_liabilities`, `selling_liabilities`, `flags`, `data`, `subentry_count`, `num_sponsoring`, `num_sponsored`, `home_domain`); Soroban RPC `getLatestLedger`, `getLedgerEntries` (contract instance keys, SAC balance keys); `simulateTransaction` with an **unsigned** envelope for SAC/SEP-41 transfers (`call`, `source` recorded); `stellar.toml` GETs (SEP-1) for SEP-8 discovery only. Third-party directory (StellarExpert) is queried only if its rate limit allows and is recorded under `directory`; if blocked, record it in `SOURCES.md` and move on (no bypass).
2. **Rules**: no login, no signup, no WAF/CAPTCHA bypass, no calls to SEP-8 approval servers (a POST may have side effects, `action_required`, per discovery note row 21 [S]); mainnet is GET and unsigned simulation only.
3. **Testnet seeding** (PFH-021/022): the only writing code. Generates throwaway keypairs with `Keypair.random()` per run, funds with Friendbot, creates issuers/trustlines/offers/contracts for a catalogue case, captures the snapshot, optionally submits one payment to record the Horizon operation result as ground truth (PFH-022). Keys are never written to disk, logged, or put in a fixture (G-SECRETS); the loader and `pnpm lint` reject seed-shaped strings; the code refuses any network except testnet (`PFH_E_CAPTURE_WRITE_ATTEMPT`). Account addresses in testnet fixtures are public and become dead once the network resets [I]; fixtures are snapshots, not live dependencies.
4. **Provenance**: every captured file has `<name>.provenance.json` with script path and commit, URLs queried, RPC/Horizon versions, ledger, capture time, `containsSecrets:false`, notes. Missing provenance is `PFH_E_FIXTURE_PROVENANCE_MISSING`.
5. **Drift**: a fixture is dated evidence. PFH-025 re-captures and diffs; a changed verdict on unchanged inputs is a finding, not a silent update.

### 2.4 Ground truth

`horizon-result` (operation result of a real testnet payment: `success`, `op_no_destination`, `op_no_trust`, `op_not_authorized`, `op_line_full`, `op_underfunded`, `other`, plus `txHash`), `simulation` (`ok` or `contract-error` with code), `out-of-band` (explicitly not derivable), `none`. Evidence tags: Horizon codes -6/-8/-7/-5 = no_trust/line_full/not_authorized/no_destination were decoded from StellaGate's published testnet tx hashes by the discovery agent [S]; re-verified by PFH-022.

## 3. Reason taxonomy (superset)

`src/taxonomy/codes.ts` (`REASON_CODES`, 70 codes at v1, `TAXONOMY_VERSION = 1`) is normative; `pfh taxonomy` prints it. Each code has `group`, `scope` (`receive`, `sender`, `meta`), `defaultSeverity`, `derivation` (`local`, `public-read`, `simulation`, `out-of-band`) and a summary.

### 3.1 How it was derived

(a) Union of the three libraries' code inventories, read from source at the pinned commits: Stellar-Preflight 32 codes (`packages/sdk/src/codes.ts`, `docs/codes.md`; the discovery note says "about 31", the source has 32), stellagate-core 25 codes (22 literals in `check.ts`/`holdability.ts` plus the three dynamic `destination_${ParseError}` values `empty`, `secret_key`, `invalid` from `address.ts`), stellar-check 18 (`DiagnosticCode`, `docs/diagnostics.md`) [P]. (b) Reasons the discovery table lists that no library implements, kept so the taxonomy does not shrink to the libraries' blind spots [S: `screen_H_P054.md` reason table rows 15, 19, 21 to 24]: `MUXED_ID_DROPPED_BY_RECEIVER`, `SAC_SENDER_DEAUTHORIZED` / `SAC_RECIPIENT_DEAUTHORIZED` / `SAC_DEAUTHORIZED_PARTY_UNKNOWN`, `REGULATED_ASSET_APPROVAL_REQUIRED`, `TOKEN_ADDRESS_FROZEN`, `TOKEN_PAUSED`, `TOKEN_IDENTITY_UNVERIFIED`, `TOKEN_ALLOWLIST_EXCLUDED`, `TOKEN_BLOCKLISTED`, `TOKEN_COMPLIANCE_REJECTED`, `NATIVE_BALANCE_CAP` (stellar-check handles it under the capacity code), `RESERVE_INSUFFICIENT_FOR_TRUSTLINE`, `SIM_ACCOUNT_OR_TRUSTLINE_MISSING`. (c) Sender-scope codes keep libraries' sender-side output (`SENDER_*`, `FEE_BUDGET_TOO_LOW`) so nothing a library says is dropped.

### 3.2 Per-library mapping

`src/taxonomy/library-maps.ts` holds `LIBRARY_INVENTORY` (the code lists, with install method and commit) and `LIBRARY_CODE_MAP`. Every library code maps to one or more canonical codes. One library code can cover several situations; the mapping lists all candidates and the adapter chooses by evidence:

| Library code | Canonical candidates | Disambiguation |
|---|---|---|
| stellagate `sac_balance_not_authorized` | `SAC_BALANCE_NOT_AUTHORIZED`, `SAC_BALANCE_NEEDS_AUTHORIZATION` | emitted at two sites in `holdability.ts`; split on message text "has not been approved" |
| stellagate `trustline_not_authorized` | `TRUSTLINE_NOT_AUTHORIZED`, `TRUSTLINE_MAINTAIN_LIABILITIES_ONLY` | its `Trustline` type has one `authorized` boolean, so it cannot tell them apart; the adapter reports the parent code and the report notes the gap |
| stellagate `memo_required` | `MEMO_REQUIRED`, `MEMO_REQUIRED_DIRECTORY` | message contains "(public directory)" |
| stellar-check `DESTINATION_NOT_AUTHORIZED` | `TRUSTLINE_NOT_AUTHORIZED`, `TRUSTLINE_MAINTAIN_LIABILITIES_ONLY` | `assess.ts` message says maintain-liabilities authorisation is insufficient; the code does not split |
| stellar-check `DESTINATION_CAPACITY_EXCEEDED` | `TRUSTLINE_LIMIT_EXCEEDED`, `NATIVE_BALANCE_CAP` | by asset (native vs credit) |
| stellar-preflight `TRANSFER_SIMULATION_FAILED` | `SIMULATION_TRANSFER_FAILED` or a refinement | the library puts the contract error name in the reason text (`simReason`); the adapter refines from the recorded contract error code |
| stellagate `destination_unfunded` | `ACCOUNT_UNFUNDED` | severity is `warn` for native, `block` for other assets |

Known cross-library severity disagreement (from source): `MEMO_REQUIRED` is `warning` in stellar-preflight and `block` in stellagate-core; stellar-check reports it as an issue (status `issues_found`). The report surfaces such cases as `severity_differs`.

### 3.3 Refinement and same-fact relations

`REFINES` (child -> parent) and `SAME_FACT` (groups of codes that name one fact differently) are exported from `codes.ts` and drive agreement levels (section 6.2).

### 3.4 Versioning

Adding, removing or renaming a code bumps `TAXONOMY_VERSION`, updates this section and `pfh taxonomy`, and is recorded in `docs/CHANGELOG.md` (repo root) because the scenario pack and reports quote codes. Codes are never reused with a different meaning.

## 4. ReceiveVerdict

TypeScript: `src/types.ts`; schema: `schemas/receive-verdict.schema.json`.

```ts
interface ReceiveVerdict {
  schema: "sik.receive-verdict/1"; adapterId; adapterVersion; caseId;
  verdict: "can_receive" | "can_receive_with_warnings" | "cannot_receive" | "unknown";
  reasons: ReasonEntry[];      // receive and meta scope
  senderSide: ReasonEntry[];   // sender scope, never affects `verdict`
  unmapped: string[];          // library codes with no mapping
  libraryStatus: string;       // READY/WARNING/BLOCKED | ok/warn/block | no_known_issues/issues_found/incomplete (verbatim)
  raw: unknown;                // library output verbatim (JSON-safe), timestamps stripped
  error?: { kind: "adapter_unavailable" | "threw" | "timeout"; message: string };
}
interface ReasonEntry { code: ReasonCode; severity: "info"|"warning"|"blocking"; party; libraryCode: string; message?: string }
```

### 4.1 Derivation (the harness decides the class, from mapped reasons, not from the library's status string)

In priority order: (1) `error` present -> `unknown`. (2) any receive-scope reason with severity `blocking` -> `cannot_receive`. (3) any meta-scope reason with severity `warning` or `blocking` (provider failure, invalid asset/amount, unsupported scenario, network mismatch) -> `unknown`. (4) any receive-scope reason with severity `warning` -> `can_receive_with_warnings`. (5) otherwise `can_receive`. `info` never changes the class. Sender-scope reasons are ignored by all steps. The library's own status is stored in `libraryStatus`; a mismatch between the derived class and a simple status mapping (READY<->can_receive, WARNING<->warnings, BLOCKED<->cannot_receive, ok/warn/block likewise, `no_known_issues`<->can_receive, `issues_found`<->cannot_receive, `incomplete`<->unknown) is reported as an informational finding, not an error: it exposes libraries whose severities are inconsistent.

### 4.2 Unmapped codes

An unmapped library code makes the run fail with `PFH_E_UNMAPPED_LIBRARY_CODE` unless `--allow-unmapped`, in which case it is listed in `unmapped` and as a finding. This is how a library upgrade that adds a code is noticed.

## 5. Library adapter interface

`src/adapters/types.ts`: `LibraryAdapter { id; info(); capabilities(); replay(case, snapshot); live?(case, options) }`. `replay` MUST be deterministic and offline: all reads are served from the snapshot. It MUST NOT throw for library failures (return a verdict with `error`). Adapters strip nondeterministic fields (timestamps, durations) from `raw`.

### 5.1 Injection points (read from source, [P] 2026-10-31)

| Library | Entry | Injection | Feeding from a snapshot |
|---|---|---|---|
| stellar-preflight | `preflight(input, {chain})` | `Chain {account, trustline, contract, sacBalance, call, errorName?}` (`packages/sdk/src/chain.ts`) | `account` from `accounts[id]` flags + `config.memo_required`; `trustline` from `accounts[id].trustlines`; `contract`/`sacBalance` from `contracts`/`sacBalances`; `call` matches a recorded simulation by canonical call string, and returns an error "no recorded simulation" otherwise (then the verdict is `unknown` for that check); `errorName` from recorded reads |
| stellagate-core | `check({to, from?, memo?, asset?, amount?, network, accounts, contracts, federation, directory})` | `AccountSource.loadAccount`, `ContractSource {contractExists, sacBalance}`, `FederationResolver`, `DirectorySource` (null to skip) (`src/sources.ts`) | `loadAccount` from `accounts` (trustlines reduced to its single `authorized` boolean, data base64); `contractExists` from `contracts`; `directory: null` unless `snapshot.directory` present |
| stellar-check | `checkPayment(intent, provider)` | `PaymentProvider {url, getNetwork(), getAccount(address), checkMemo(payment)}` (`src/types.ts`) | `getAccount` returns Horizon-shaped account JSON rebuilt from the snapshot (balances with `asset_type`, `is_authorized`, limits and liabilities, `subentry_count`, `num_sponsoring/ed`); `getNetwork` from `networkParams` and `ledger`; `checkMemo` from the data entry. `PaymentIntent.source` is required, so cases without a sender use the case's `referenceSender` (a funded account in the snapshot); sender-side output is kept in `senderSide` |

### 5.2 Capabilities

`AdapterCapabilities` (classic/native/muxed/contract destination, SAC transfer, SEP-41, memo, federation, distinguishes maintain-liabilities, accepts injected state, requires sender, uses sender for simulation) are stated per adapter in `src/adapters/*.ts` from the source reading; PFH-013 verifies each against behaviour. A case a library does not claim to cover is `applicable: false` for it (shown "n/a", never a gap). Current claims: stellar-check does not claim muxed, contract, SAC or SEP-41 destinations (its own tests treat M/federation/Soroban as out of scope [P: `docs/fixtures.md` group 27]); stellagate-core claims no SAC transfer simulation and no SEP-41; stellar-preflight claims all but federation.

### 5.3 Live mode

`pfh run --live` calls the library against the network read-only (`live()`), for spot checks and fixture refresh. Live results are never mixed into the fixture-based headline numbers.

## 6. Comparison and report

### 6.1 Matrix

One row per case, one cell per adapter: derived class, receive codes, sender codes, worst receive severity, applicability, error. Row agreement: `unanimous`, `split`, or `unanimous-unknown`.

### 6.2 Agreement levels (per pair of applicable adapters)

L0 exact (same class and same receive-code set); L1 refinement (same class, equal after replacing each code by its `REFINES` ancestors and merging `SAME_FACT`); L2 class-only (same class, different facts); L3 differ (classes differ). A row is `unanimous` when every pair is L0 or L1.

### 6.3 Findings

`verdict_class_differs`, `reason_set_differs`, `severity_differs`, `coverage_gap` (an applicable adapter omits a code the catalogue says a correct complete library should report, closure applied), `differs_from_expected` (class differs from the catalogue expectation when that is not `undetermined` and the answer is not `unknown`; carries the expectation's trust tag and a plain-text relation to the recorded result; an authored judgement, never counted as an error), `abstained` (the library answered `unknown` where the catalogue expects a verdict; a scope/coverage fact, grouped with gaps), `contradicts_ground_truth` (class implies success but the Horizon result/simulation is a failure, or the reverse; not evaluated for cases tagged `@not-derivable`), `scope_leak` (a sender-scope condition changed the receive class), `adapter_error`, `unmapped_code`. Each finding has case, adapters, codes and a one-line detail. The report separates **disagreements** (libraries disagree), **gaps** (a library is silent), **expectation differences** (a verdict differs from a trust-tagged authored expectation), and **errors** (a verdict contradicts a recorded ledger or simulation result, or a library failed). Only errors are claims about evidence.

### 6.4 Outputs

`out/report.json` (`DiffReport`, keys in stable order so two runs diff cleanly) and `out/report.md`: header (taxonomy version, adapter versions and commits, fixture ledger range, counts of captured vs catalogued vs synthetic cases), the matrix table, findings grouped by kind with the case and code, a per-case appendix with each library's verbatim status and reasons, and a "not evaluated" section listing uncaptured cases. Numbers in the headline count captured, non-synthetic cases only.

### 6.5 Determinism

Same fixtures + same library versions -> byte-identical report. Report generation reads no clock except the `generatedAt` header, which is excluded from the comparison used by `pfh report --check`.

## 9. DTC registered-wallet readiness scenario pack

### 9.1 Principle

Requirements are data (docs/ARCHITECTURE.md principle 3). dtc-kit owns the requirement rows; this project **references** rows by id and never redefines them. At scaffold time dtc-kit's profile files exist (`projects/dtc-kit/packages/profile-spec/profiles/dtc-generic.json` and `dtc-stellar.json`, both version `2026-10-31`, read 2026-10-31 [P]); every Stellar row is `inferred` or `unknown`, and the profile disclaimer is: "DTC-shaped, not DTC-certified. Every Stellar row in this profile is inferred or unknown: DTCC has published no Stellar wallet, token or API requirements. Do not describe any output built on these rows as DTC-compatible." Every output of this section MUST carry that disclaimer (copied at export time, PFH-027).

### 9.2 Scenarios

Definitions: `src/dtc/scenarios.ts` (`DTC_SCENARIOS`, 12; each has an append-only `sc` number used as `SC-NNN` in the pack). A scenario's status tag is the **weakest** status among its referenced rows (`scenarioStatusTag`), so a scenario resting on an `unknown` row is `@unknown` and is never presented as fact (G-DTCC).

### 9.3 Evaluator

`evaluateDtcReadiness(input, snapshot, receiveVerdicts)` (PFH-026) returns `readiness` (`ready | not-ready | unknown`), `dtcReasons` and the receive verdicts it used. DTC-specific checks use the snapshot only: asset flags (`AUTH_REQUIRED`, `AUTH_CLAWBACK_ENABLED`), wallet address kind (G / M / C), whole-token amount (units divisible by 10^7 stroops for a 7-decimal classic asset), reserve headroom for a trustline, SEP-57 identity read where recorded. Readiness is `unknown` when the decisive row is `unknown` (wallet kind, chill mapping). `ready` requires: no blocking receive reasons from any applicable library that the scenario designates as reference, no DTC reasons, and no `unknown` decisive row.

### 9.4 Scenario-pack export (dtc-kit's ScenarioPack contract)

`docs/ARCHITECTURE.md` lists `ScenarioPack format (tagged scenarios)`, owner `dtc-kit/conformance`, consumers token-invariants and preflight-harness. When this scaffold started the repository had no schema for it; **by the time of the final check on 2026-10-31 dtc-kit had published one**: `projects/dtc-kit/packages/conformance/schema/scenario-pack.schema.json` (JSON Schema 2020-12, `packFormat: "1"`), described in `projects/dtc-kit/SPEC.md` section 5.1, with an example pack `packs/dtc-kit-readiness.pack.json` [P: read 2026-10-31]. The exporter (`src/export/scenario-pack.ts`, real) mirrors that shape in local types (no import of dtc-kit source, ADR-0002) and the smoke test validates the exported pack against the owner's schema when the sibling file is present (path overridable with `DTC_KIT_SCENARIO_PACK_SCHEMA`).

Mapping (all tested): pack `packFormat "1"`, `packId "preflight-harness-dtc-wallet-readiness"`, `profile "dtc-stellar"`, `version` = date, disclaimer carried verbatim; scenario `id` `SC-NNN` from the append-only `sc` number in `DTC_SCENARIOS`; `area` from the dtc-kit enum; `tags` = exactly one trust tag equal to the weakest status among `requiresRows` (dtc-kit's own rule) plus the adapter/run tags from `docs/CONVENTIONS.md` (`@stellar-sac @stellar-sep57 @testnet @slow`); `requiresRows` = row ids; `onUnknown` = `run-and-label` when any row is `unknown`, else `skip`; `given`/`when`/`then` are human-readable strings (the contract's shape), with the machine-checkable expectations living in `DtcScenarioDef.expect` and in our evaluator; `status` = `catalogue` until dtc-kit's runner can call our evaluator, `ticket` = the implementing ticket.

**Known mismatch with the contract (open, cross-project request):** the schema requires `ticket` to match `^DTC-[0-9]{3}$`; scenarios produced here are implemented by `PFH-NNN` tickets, so the exported pack fails exactly that one constraint (12 errors, all `pattern` on `/scenarios/N/ticket`; the smoke test asserts nothing else fails). Ask dtc-kit to widen the pattern to `^[A-Z]{3}-[0-9]{3}$` (the same issue affects token-invariants). Until then the exporter emits `PFH-026` rather than falsifying a DTC ticket id.

**We do not define or run dtc-kit's runner.** Whether dtc-kit's `runPack` can execute a scenario that needs a different project's evaluator is dtc-kit's decision; until it can, our scenarios stay `catalogue`.
